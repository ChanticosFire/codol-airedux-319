## 3. 关键技术发现（对同引擎项目可能有复用价值）

### 3.1 快照头（逐字节，对照 `cols` 的写入器得到）

| 偏移 | 字段 | 我们发 |
|---|---|---|
| 0 | `svc_snapshot` | `0x00` |
| 1..4 | `serverTime` LE | 72200 |
| 5 | `delta_distance` | `0x00` |
| **6** | **`flags`**（建立 baseline 时为 `8`，否则 `0`） | `0x0C` |
| 7… | 位域：`1` 无前置 ps + `1` 传 origin + **`8` 位 `last_changed+1`** + `1` 位 gap + `1` 位 `-97` | |
| 之后 | **4 字节 `commandTime`** | |

**注意**：`last_changed` 是 **8 位**，这是与 3.3.3.3 世代最容易搞错的一处。

### 3.2 快照内容块只有 5 个

全 `.text` 扫描每个入口的调用点，**各自只有一个**，全部在 `0x4723C4..0x4724CD` 的调度器内：

| 调用点 | 入口 | 块 |
|---|---|---|
| `0x4723DD` | `0x471D80` | entities |
| `0x472401` | `0x471980` | playerState |
| `0x472424` | `0x471010` | actors |
| `0x472445` | `0x471560` | 未识别 |
| `0x4724A0` | `0x4475F0` | glass |

`0x671D80` **只是头解析器**，它不调用任何内容块。

### 3.3 实体列表的位布局（这一块最容易错）

`0x671650` 的流程：

- **门控位 1 = 正文 bit 1307**（`0x671678`），为 0 则整块跳过；
- **门控位 2 = bit 1308**（`0x671685`）；
- **计数 = `buffer[164]` 的一个整字节**（`0x66ED70` 读取后存到 `0x7859558`）；
- **实体 ID = 12 位，但 `0x66EC30` 跨字节时从"字节游标"续读，因此跳过 byte 164**。

实测验证过的组装式：

```
id = ((byte163 >> 5) & 7) | (byte165 << 3) | ((byte166 & 1) << 11)
```

用 `byte163=0x18, byte164=0x01, byte165=0x01, byte166=0x1E` 得到 **`eax = 8`**，与预测一致。

### 3.4 每实体增量是"模式操作序列"，不是字段循环

`0x471E03` 读 1 位 `changed`：1 → 复制 52 字节；**0 → `call 0x671700`**（增量解码器）。

`0x671700` 先读一个变长**模式选择器**，再 `jmp [mode-1 * 4 + 0x671B2C]`（13 项跳转表）：

- **模式 3**（`0x6717A1`）：读 11 位 → `[stream+0x24]`（暂存）
- **模式 4**（`0x6717B5`）：读一个 `-97` 值 → `[stream+0x28]`（暂存）
- **模式 1**（`0x671890`）：**提交** —— 写 `[edi+0x10]`、`[edi+8]`、`[edi+0x30]`、`[edi+0x18]`，**并把三个浮点写到 `[edi+0x24]`、`[edi+0x2C]`、`[edi+0x28]`（即 origin）**

### 3.5 位置分量的编码

每个分量由 `0x6715D0` / `0x6714D0` / `0x671550` 内联读取：

- **gate 1 位**（0 = 该分量不变）
- **scale 1 位**（1 → 常量 `0xDB1118` = **5.0**；0 → 1.0）
- **value 5 位**

即 7 位/分量，位移量 = `value × 1.0` 或 `value × 5.0`。

## 4. 卡点（精确）

客户端画面是**黑屏 + 右下角转圈**。两张间隔 1 秒的截图**不同**（10752 / 10690 字节），**说明转圈在动 —— 它确实在等，不是画不出来**。

调用链（全部实测）：

```
ui_state (0x84ABA50) == 5        ← 前端"等待"画面
  ↑ 由 0x803780 决定：读单例 [0x8269774]（0x803830 惰性创建，0x1618 字节）
  ↑ 经 0xB7A670 → 0xBA0780 映射
  ↑ 映射结果 == 2 时，0x8037D6 选 ui_state = 5
  ↑ 关键字段 [sub+0x5E8]（sub = [单例+0x4F4]）
     实测： [+0xC8] = 2   [+0x644] = 0   [+0x5E8] = 3
     代码 0xBA07A4 处 sete al ; inc eax  →  [+0x5E8] == 3 恰好产出状态 2
  ↑ [sub+0x5E8] = 3 由 0xBA3C47 写入
  ↑ 前提：[obj+0x5FC] 处 8 字节与调用者提供的 8 字节相等（0xBA3C05..0xBA3C1A，call 0xB73FE0）
     —— 读起来就是"会话令牌匹配"
```

**所以：客户端已经匹配了会话令牌，停在"已匹配、等待中"的状态 3。**
**未定位的是"离开状态 3"的那次转换**（状态 0/1/2 的写入点分别在 `0xBA3460`、`0xBA3252`、`0xBA3DA3`）。

因为令牌检查已通过，**该转换最可能是由"服务端还没发的某条会话级消息"或"某个计时器"触发**，而不是令牌本身。

## 5. 走过的误区（写出来避免别人重复）

这些每一条都曾被我当作前提，后来被实测推翻：

1. **"网络状态 10 = 进入对局"** —— 错。状态 10 且实体计数 1 时，截图仍是黑屏转圈。**`state 10` 只代表网络握手完成。**
2. **"`0x671D80` 会调用实体块"** —— 错，它只是头解析器；内容块由 `0x4723xx` 调度。
3. **"实体 ID 是 bit 1309 起的连续 12 位"** —— 错，是三段式且**跳过 byte 164**（因为跨字节续读用的是字节游标）。
4. **"`PsField`(`0x6701D0`) 是 playerState 专用"** —— 错，它是通用字段 codec，实体块也会调。
5. **"1649370 有 14 个 section"** —— 错，是 **5 个**（14 是 3.3.3.3 世代的数字）。
6. **"快照有两个独立游标"** —— 部分错：`[+0x1C]` 是字节索引、`[+0x20]` 是绝对位位置，**是同一位置的两种单位**。
7. **"加载对象非空 = 还在加载"** —— 一度因此误判为"已进图但未绘制"，又用截图差分纠正回"确实在加载"。
8. **最根本的一条**：早期几十轮在**从不会被执行的分支**上优化内容（例如在空的 playerState 块后面加字段）。**判据错了，编码再对也没有意义。**
