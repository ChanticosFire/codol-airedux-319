# Build 1649370：物品 ID、SKU 与对局武器索引边界（2026-10-30）

## 本轮假设与结论

本轮验证用户转来的 `旧表物品 ID + 9000` 是否能用于当前 319 服务；若为真，当前目录应把 `type95_mp` 的物品 ID 记为 `10000`，且有相应 SKU→商品→物品的可核对链路。实际当前工作树附带的社区目录把 `1000` 记为 `wea/type95_mp`、`10000` 记为 `bdg/badge_xpboost`，因此**不能把 +9000 当成当前服务的通用换算**。用户资料可能对应另一版完整目录；其抓包和完整目录尚未在本工作树验证。

| 旧社区种子物品 ID | `items_cha_unlockall.proposed:406` 为 `1000 type95_mp`，`:461` 为 `1055 ak104_mp` | 是这份种子的数字；不是零售目录的实机证据 |

上述社区目录两条绝对路径：`他人文件参考/修正-发布v0.0.7-rc.1_解压/修复工作副本/服务端/bd_data/items_cha_unlockall.proposed`、同目录 `marketplace_catalogue.json`。r525/r527 对照在 `evidence/experiments/20261026-r527-warehouse-control.json`。用户聊天里引用的 `F:\CODOL\其他项目参考\codol服务端v1.1` 和另一份完整目录路径当前机器未找到，未核对其源码或 SHA；`10710`/`10690`/`1609` 的关系保持**未验证**。

2026-10-30 补充：聊天记录本身给出 `1609+9000=10609`，同时称“熔岩真实 ID 是 10690”、客户端发送 SKU `10710`。这三个数字不能直接互推，尤其 SKU 与物品 ID 属不同字段。当前能使用的是**按内部名称比对两版目录的调查方法**，以及对真实客户端请求记录原始 SKU 的提示；`+9000` 目前只在聊天所引的旧表枪械样本中成立，不能推广到角色、道具、当前 319 库存或对局快照。该资料也没有给出导致本 Build `usercmd.weapon=0` 的直接证据。

## 可用的工作方向

1. 先对一条**当前 Build 原生请求**读取 service、task、SKU 原值，再对照**同版本** SKU→product→item 目录，不跨目录推算。库存若持久化，核对入库 item ID、响应 item ID 与客户端 UI 接收值是否一致；不要批量改写 7208 项现有档案。
2. 排查赛后仓库空白时，先比较 r525/r527 的原生 `inventory_state`、`initial_fetch_bits`、`store_state` 与实际请求/应答。r527 在相同保存保护下有完整仓库，因此“保存保护造成空仓库”已被反例否定，赛后状态转换仍未定位。
3. 原生射击卡点仍是 r811 真实攻击包 `usercmd.weapon=0`，同时玩家状态武器 78；先追客户端命令武器生产与快照尾部装备消费。商城 SKU 资料只可能帮助账户/配装链路，**尚无证据**把它与命令武器 0 建立因果。

本轮只作静态核对，没有修改商城目录、库存、档案、LSG 或对局编码，也没有启动客户端。保留现有私有档案基线和唯一 `r107flow/runtime`。
